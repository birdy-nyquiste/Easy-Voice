### H1. Email regex has quadratic backtracking: an unauthenticated login POST can pin the CPU for minutes

[src/server/auth.ts:32](../src/server/auth.ts#L32) · security

requestEmailOtp checks the raw email against `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` with no length cap. The domain part `[^\s@]+\.[^\s@]+$` backtracks in O(n^2) when the input has many dots and fails at the end. Measured locally: 80 KB takes 2.3 s and 160 KB takes 9.5 s, so 1 MB runs for minutes. loginAction needs no sign-in and runs this check whenever `intent=send` or the client-supplied `prev.step === 'email'`. next.config.ts:17 raises the body limit for every server action, including loginAction, to 4.5 MB.

**Scenario:** An attacker takes the login action id from the login page's JS bundle and POSTs `email = 'a@' + 'a.'.repeat(500000) + '@'`. The regex blocks the Node event loop until the function hits its time limit. On Vercel Fluid compute, other requests on the same instance (other users' page loads, Telnyx call webhooks) stall too, and each request bills minutes of CPU time. A few requests per minute keep the app degraded.

**Fix:** Reject `email.length > 254` before the regex, and switch to a pattern without overlapping quantifiers, e.g. `/^[^\s@]+@[^\s@.]+(\.[^\s@.]+)+$/`. Optionally lower the server-action body limit back to the default and raise it only for the voice-clone upload.

**Verifier:** UPHELD: Confirmed. requestEmailOtp (auth.ts:32) runs /^[^\s@]+@[^\s@]+\.[^\s@]+$/ on the raw email with no length cap. loginAction (app/login/actions.ts) is an unauthenticated server action and reaches requestEmailOtp when intent=send or the client-supplied prev.step === 'email'. Nothing parses or validates the email first: only String(), trim() and toLowerCase(). I timed it locally with 'a@' + 'a.'.repeat(n) + '@': 10 KB took 38 ms, 20 KB 146 ms, 40 KB 577 ms and 80 KB 2.37 s, which is clearly quadratic. Extrapolated, 1 MB runs about 6 minutes and 4.5 MB much longer. next.config.ts raises bodySizeLimit to 4.5 MB for every server action, though even the 1 MB default would be enough to exploit. Server-action origin checks don't stop a non-browser client. Each request pins a CPU core until the function's time limit, so a handful of requests degrades the app and drives up compute cost. Unauthenticated and trivial to trigger, with a one-line fix (cap at 254 chars plus a non-overlapping pattern). High.

### H2. OTP attempt cap and hourly send limit can be bypassed with parallel requests (lost-update counters)

[src/server/auth.ts:64](../src/server/auth.ts#L64) · security

verifyEmailOtp reads the newest OTP row, checks `otp.attempts >= OTP_MAX_ATTEMPTS` in JS, then on a wrong code writes the absolute value `attempts: otp.attempts + 1` from the value it read earlier. The read, check and write are separate statements with no transaction, row lock or conditional update, so concurrent guesses all read the same counter, all get compared, and all write the same n+1. The success path also sets consumedAt without `consumed_at IS NULL`, so one code can be redeemed more than once concurrently. requestEmailOtp has the same count-then-insert race (count rows, then insert), so parallel requests exceed OTP_MAX_PER_HOUR and each extra code starts with attempts=0. There is no other throttle on verify (no middleware, no per-IP limit, unauthenticated server action), so the 5-guess cap is the only brute-force guard on a 1e6 code space.

**Scenario:** An attacker requests a code for victim@example.com, then sends waves of ~200-2,000 concurrent loginAction POSTs (prev.step='code'), each with a different 6-digit guess. Each wave reads attempts=k and writes k+1, so a few waves test thousands of codes instead of 5. At 5 codes/hour (more through the send race) that is tens of thousands of guesses per hour, a realistic path to taking over the account (balance, numbers, recordings, texts) within days.

**Fix:** Spend the attempt atomically before comparing: `UPDATE email_otps SET attempts = attempts + 1 WHERE id = $id AND consumed_at IS NULL AND attempts < 5 RETURNING *`; if no row comes back, treat the code as exhausted, and only then compare the hash. Consume with `UPDATE ... SET consumed_at = now() WHERE id = $id AND consumed_at IS NULL RETURNING id` and create a session only if a row was returned. Do the per-email hourly count and insert under a per-email advisory lock (like withUserLock) or as one guarded INSERT ... SELECT. Consider a per-IP limit on loginAction. Add a test that fires ~20 concurrent wrong guesses and asserts a later correct guess is refused.

**Verifier:** UPHELD: Confirmed. verifyEmailOtp (auth.ts:51-70) reads the newest unconsumed OTP, checks otp.attempts >= 5 in JS, and on a mismatch writes the absolute value attempts: otp.attempts + 1. That write runs in a separate statement with no transaction, row lock or conditional WHERE. The consume update also has no 'consumed_at IS NULL' guard. requestEmailOtp (auth.ts:34-45) counts and then inserts without a lock, unlike withUserLock elsewhere. There is no middleware or proxy and no per-IP or per-email throttle, and loginAction is unauthenticated. Each request's SELECT runs before its own UPDATE, and postgres.js queues queries on a pool of 10 per instance across many Vercel instances. So a burst of hundreds of concurrent guesses mostly reads the same attempts value, and each wave spends roughly one attempt. With about 1,000 guesses per wave, 5 waves per code and 5+ codes per hour against a 1e6 code space, takeover becomes likely within about a day. The victim gets the OTP emails but cannot stop the attack. The double-consume part is minor, since both sessions belong to whoever has the code, but the core lost-update bypass of the only brute-force guard is a real auth weakness. High.

### M1. Every timestamp is rendered in the server's time zone (UTC on Vercel), with no zone label and no year

[src/lib/format.ts:48](../src/lib/format.ts#L48) · i18n

formatDateTime calls `new Date(d).toLocaleString(BCP47[locale], {month, day, hour, minute})` with no timeZone. Every caller is a server component (dashboard recent calls, calls list and detail, messages list and thread, billing ledger and payments, number 'Renews {date}', the API-key 'rejected on {date}' notice), so times come out in the server process's zone, which is UTC on Vercel, with no zone name. next-intl's getRequestConfig (src/i18n/request.ts:22) sets no timeZone either, and nothing in SPEC records UTC display as intended. In `next dev` the server zone equals the developer's, so it never shows locally. The format also omits the year although the ledger and message rows are kept indefinitely, and 'Renews {date}' shows a clock time for what is a date. The only zone handling in the app (agent form) already reads the browser zone via Intl.DateTimeFormat().resolvedOptions().timeZone.

**Scenario:** A user in California receives a call at 3:05 PM PDT on Oct 21. /calls, the dashboard and the call header show 'Oct 21, 10:05 PM'; a text received at 8 PM local shows as Oct 22; a top-up at 5:30 PM Nov 3 shows 'Nov 4, 1:30 AM' in billing. Shanghai users see times 8 hours off. A ledger entry from 2025-10-21 and one from 2026-10-21 both read 'Oct 21, ...'.

**Fix:** Format in the viewer's zone: either a small client <LocalTime iso=...> component that formats with the browser's Intl (suppressHydrationWarning or render after mount), or store the browser's IANA zone in a cookie (like ev_locale/ev_sidebar) or on the user row and pass it as `timeZone` to formatDateTime and from getRequestConfig. At minimum add `timeZoneName: 'short'`. Add `year: 'numeric'` when the date is not in the current year, use a date-only format for 'Renews {date}', and add a unit test that pins timeZone so output doesn't depend on the host.

**Verifier:** UPHELD: Confirmed. formatDateTime (src/lib/format.ts:46-54) calls toLocaleString with no timeZone. All callers are server components (I checked calls, billing, dashboard, messages and numbers pages; none is 'use client'). getRequestConfig (src/i18n/request.ts) sets no timeZone. README/SPEC say the app deploys to Vercel, where the server runs in UTC. Nothing in SPEC says UTC display is intended. SPEC §422 even notes that Telnyx's own times default to UTC, which is why `current_time` uses the agent's time zone, so the author does care about zones. The result is that US users see call, message and ledger times 4-8 hours off, with no zone label. The missing year and the time shown in 'Renews {date}' are smaller polish points. This is a real, visible correctness bug, but only in display (no money or data impact), so medium rather than high.

### M2. call.answered and call.hangup are applied without ordering or atomic guards, so answered calls can go unbilled or stay 'answered' and block the user

[src/server/calls/events.ts:180](../src/server/calls/events.ts#L180) · data-integrity

Billing depends on calls.answered_at, which only onAnswered sets. onAnswered reads the row, checks status === 'initiated', then runs an unconditional `update calls set status='answered', answeredAt` filtered only by id. onHangup does the same kind of read-then-write and chooses between billing and 'failed' based only on `call.answeredAt` as it was read. docs/telnyx-api-notes.md §6 says deliveries can arrive out of order, and nothing here handles that. For inbound calls the assistant starts with the answer command, not with this webhook, so the conversation happens regardless. hasOtherActiveCall (state.ts:14-27) treats initiated/answered as active and never checks endedAt, so a row left 'answered' with endedAt set counts as an active call.

**Scenario:** (1) Out of order: an inbound call is answered and call.answered gets a transient 500 (cold start, DB timeout) or simply arrives late. The caller talks for 12 minutes and hangs up. call.hangup is processed first: answeredAt is null, so the row becomes 'failed' with billedCents 0, resultsFetched true and outcome 'Call ended before connecting (normal_clearing)'. The retried call.answered sees status != 'initiated' and returns. The conversation is never billed ($1.80 lost while Telnyx bills the platform) and its transcript is never fetched. (2) Concurrent: on a short call two instances handle answered and hangup at once; onHangup commits failed with endedAt set, then onAnswered's unconditional update writes 'answered'. The row is 'answered' with endedAt set, never billed, and hasOtherActiveCall rejects every inbound call with USER_BUSY and outbound with 'callInProgress' for 4 hours; the calls list keeps AutoRefresh running because inFlight looks only at status.

**Fix:** Make transitions conditional and atomic. In onAnswered use `update ... where id=? and status='initiated' and ended_at is null returning`. If no row comes back because the call already ended without answeredAt (and it is neither rejected nor chargeWaived; for inbound the assistant ran), backfill answeredAt from the event and bill (endedAt - answeredAt) with the same idempotency key `call:${id}` in one transaction. In onHangup add `ended_at is null` to the WHERE clause and branch on the row actually updated. Alternatively run both handlers under withUserLock and re-read inside the lock. Add `isNull(calls.endedAt)` to hasOtherActiveCall and to the page's inFlight check.

**Verifier:** UPHELD: Confirmed. onAnswered (events.ts:179-181) reads the row, checks status === 'initiated', then updates by id only. onHangup (229-281) chooses between billing and 'failed' based on the answeredAt value it read earlier, with no conditional WHERE and no lock. docs/telnyx-api-notes.md §6 says deliveries can be out of order. withWebhookDedupe deletes the dedupe row when the handler throws, so a retried call.answered can arrive after call.hangup was processed; it then sees status 'failed' and returns, and the conversation is never billed. In the concurrent case, the stale onAnswered write can leave status 'answered' with endedAt set. hasOtherActiveCall (state.ts:14-27) filters only on status and createdAt, so that row blocks inbound and outbound calls for 4 hours, and the calls page's inFlight check (calls/page.tsx:38) keeps AutoRefresh running. Both triggers are uncommon: one needs a race of a few milliseconds, the other needs the answered retry to arrive after the call has ended. That makes high too strong; the consequences (unbilled minutes, a 4-hour lockout) justify medium.

### M3. Late provider data after a call is purged or deleted: recording left at Telnyx forever, transcript written back onto a deleted call

[src/server/calls/events.ts:284](../src/server/calls/events.ts#L284) · data-integrity

**Verifier:** UPHELD: Confirmed. deleteCallRecord (calls/index.ts:135-141) needs only endedAt. purgeCallContent calls purgeCallData, which lists recordings by call_control_id (live.ts:472-476) and deletes only those it finds, then sets purgedAt. onRecordingSaved (events.ts:284-288) sets hasRecording=true without checking purgedAt or deletedAt and never purges again. A recording saved after the delete therefore stays at Telnyx, against SPEC §16 (30-day deletion and user deletion). Likewise, fetchCallResults (results.ts:11-19) checks purgedAt on the row it was given, makes a slow provider call, then updates by id only. A page refresh or the fetchCallResultsSoon timer running at the same time as a delete can write the transcript and summary back onto a purged, deleted row, where they stay hidden but permanently stored. It only happens when a user deletes within seconds of hangup, but it breaks a stated deletion promise. Medium is appropriate.
